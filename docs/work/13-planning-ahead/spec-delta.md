# Spec delta — planning ahead, several focus sentences, manual backlog order

Amendment 1 to `docs/SPEC.md`. Read that document's §6 for the rule-by-rule before/after; this file is
what a builder needs to scope and start.

**In SPEC:** 30 rules added (125 → 155), 54 scenarios added (103 → 157), 31 existing rules marked `⚠`
superseded or modified, 4 scenarios retired / re-pointed / narrowed.

---

## 1. The change, for a builder

Four product changes, one coherent feature.

1. **Several weekly focus sentences per leaf, per week.** `weekly_focus` stops being unique on
   `(user, goal, week)`. A leaf holds **1–5** rows for a week, ordered by an integer `sortKey` assigned
   from entry order on every plan save. Zero rows still means dormant, so **"active" becomes "has at
   least one row"** and every rule built on active/dormant survives untouched — they all already asked
   "is there a row?", never "is there exactly one?" (R-plan-13, R-plan-14, R-goal-9).
2. **Plan the current week and the next four.** `PLAN_AHEAD_WEEKS = 4`. Offsets `0 … +4` are writable;
   everything `< 0` is readable and **never** writable, which is D-2 unchanged — history stays truthful.
   Four is a validation bound, not a picker clamp: the 8-week history bound limits a control over weeks
   that already exist, whereas every week in the forward window is one a write would *create*. Current
   week + 4 covers 35 days, i.e. any calendar month; beyond that the product's unit is the goal's
   `period` and Re-plan, not a weekly focus (R-plan-15, R-plan-16, R-plan-17).
3. **Tasks in future weeks.** `originWeek` becomes the *target* week rather than always the current one —
   still server-assigned, still immutable, still no back-dating. A backlog pull takes a target week too.
   Completion stays bounded by `originWeek ≤ week ≤ currentWeek`, so **a future-dated task cannot be
   completed at all until its week arrives**; Move-to-Backlog and Cancel still work on it, so no fourth
   exit appears. Carry age is clamped — `max(0, weeksBetween(origin, min(viewed, current)))` — which is
   what keeps the red chip off work nobody is late with, and keeps every existing carry scenario passing
   verbatim (R-task-34 … R-task-38).
4. **Manual per-goal backlog order.** `BacklogItem.sortKey`, an opaque lexicographic string, unique
   within `(owner, goal)`. New items land at the top; a move to another goal re-keys to the top of the
   destination; conversion and delete leave gaps. Reorder is one **relative** command (`after` / `before`
   / `top` / `bottom`), never a position index. Manual order exists **only within one goal** — the
   Life-goal aggregate and the group ordering on the Backlog page stay `capturedAt` desc
   (R-backlog-17 … R-backlog-21, R-backlog-25).

Two rulings worth reading before you start:

- **Tasks do not attach to a focus sentence** — not required, and not optionally either. A required field
  breaks "nothing is mandatory"; an optional one creates two classes of task, a rendering fork on every
  surface, and a lifecycle rule for a pointer the whole-week replace can delete underneath it. Worse, a
  focus row is per-week while an open task carries across weeks, so a week-`n+3` task pointing at a
  week-`n` sentence is a reference whose meaning decays — D-1 in a different column. **Lost:** you cannot
  ask which sentence a task served, and tasks cannot be grouped by sentence. Accepted (R-task-33).
- **Drag is never the only way to re-order.** Keyboard grab mode, a visible always-rendered reorder
  control, menu items, and a defined set of screen-reader announcements are requirements of the feature,
  not follow-ups. `tests/screens/sheetDismissal.test.tsx` and `contrast.test.ts` already enforce the
  accessibility pass; a drag-only list regresses it (R-backlog-22 … R-backlog-24).

## 2. Migration and compatibility

A shared-schema change breaks both sides at once. Everything that moves is enumerated here.

### 2.1 Database — one new migration (`0002_*`)

`apps/api/migrations/` currently holds `0000_lovely_cammi.sql` and `0001_busy_mentor.sql` plus
`meta/_journal.json` and the snapshots, which **must be regenerated by drizzle-kit, never hand-edited**.

```sql
-- weekly_focus: drop the one-per-week constraint, add the order column
DROP INDEX `ux_weekly_focus_goal_week`;
ALTER TABLE `weekly_focus` ADD COLUMN `sort_key` INTEGER NOT NULL DEFAULT 0;
CREATE UNIQUE INDEX `ux_weekly_focus_goal_week_sort`
  ON `weekly_focus` (`user_id`,`goal_id`,`week_start`,`sort_key`);
-- `ix_weekly_focus_week` is unchanged.

-- backlog_items: the manual order column
ALTER TABLE `backlog_items` ADD COLUMN `sort_key` TEXT NOT NULL DEFAULT '';
CREATE INDEX `ix_backlog_goal_sort` ON `backlog_items` (`user_id`,`goal_id`,`status`,`sort_key`,`id`);
-- `ix_backlog_owner` (user,status,captured_at,id) stays: it still serves the cross-goal lists,
-- which keep `capturedAt` desc (R-backlog-21).
```

**Existing rows survive with no data loss, and no order changes:**

- `weekly_focus` — every existing `(user, goal, week)` has exactly one row, so `sort_key DEFAULT 0`
  satisfies the new unique index with **zero backfill**. Every existing sentence keeps its id,
  `createdAt` and `updatedAt`, and renders as the leaf's first (only) sentence.
- `backlog_items` — a backfill **is** required, or every row ties on `''` and the order falls back to
  `capturedAt` desc, which happens to be exactly today's order but leaves no key space above the top
  item. Seed in the same migration, per `(user_id, goal_id)`, in today's order:
  `ROW_NUMBER() OVER (PARTITION BY user_id, goal_id ORDER BY captured_at DESC, id DESC)` →
  `printf('%012d', rn * 1000000)`. Fixed width makes lexicographic order equal numeric order, the
  1,000,000 gap leaves room for mid-points, and starting at `000001000000` leaves room *above* the first
  item so a new capture can land on top without a re-key. **Verify `UPDATE … FROM` and window-function
  support against the deployed D1 SQLite build before relying on pure SQL**; a two-statement backfill or
  a one-shot script is an acceptable fallback (open question 5).
- No column is dropped, no row is deleted, no id changes. The migration is forward-only; a rollback
  needs the reverse index swap and is only safe while no leaf holds a second sentence.

### 2.3 The four silent breaks

Each of these compiles, passes types, and is wrong at runtime.

1. **`CompleteTaskRequest.week` loses its guard** the moment `WeekOffset` widens (§2.2 #17).
2. **`goal.service.ts snapshot()` builds `focusByGoal: Map<goalId, sentence>`** — the instant the unique
   index is dropped it silently keeps one row per goal and discards the rest. Nothing throws; the UI just
   shows one sentence. This is the highest-risk line in the change.
3. **`IWeeklyFocusRepo.findByGoalAndWeek` returns a single row** (`d1-goal.repo.ts` uses `.get()`), and
   `task.service.ts:435`, `capture.service.ts:226` and `plan.service.ts` all assume at-most-one. Must
   become `listByGoalAndWeek(): WeeklyFocus[]`.
4. **`plan.service.save` de-dupes entries into `Map<goalId, sentence>` and derives
   `expectedChanges: existing.length`** for the `GuardedBatch` precondition — both are wrong with
   multi-row weeks, and a wrong `expectedChanges` fails a valid save rather than corrupting one, so it
   will show up as a mysterious 409 rather than a data bug.

## 4. Open questions for the owner

1. **`docs/BUSINESS-RULES.md` contradicts the amendment in three places** and is shipped verbatim to
   agents as `goalcascade://rules/business-rules`, pinned by a byte-equality test. It is the authoritative
   prose and was left untouched here deliberately. `[recommended]` Amend three bullets: §Weekly focus
   bullet 1 ("one sentence per leaf per week" → "one to five, current week and the next four"),
   §Task week model ("offsets ≤ 0; future weeks not selectable" → the plannable window), §Backlog bullet 5
   ("newest first" → "newest first by default; manually re-orderable within a goal"). Nothing else moves.
2. **Is 4 the right forward cap?** `[recommended]` Yes — current week + 4 = 35 days covers any calendar
   month, and staleness scales with distance. 8 (symmetric with history) doubles the rot surface to buy a
   horizon the product has no unit for.
3. **Five sentences per leaf per week?** `[recommended]` Yes. A leaf that needs a sixth is writing a task
   list into the plan, and the cap is the only thing preventing that drift.
4. **Replace `GoalView.focus` with `focuses[]`, or keep both?** `[recommended]` Replace. Keeping `focus`
   as "the first one" gives two fields that disagree the moment a leaf has two sentences, and every
   single-line surface would keep reading the stale one.
5. **`sortKey` encoding.** `[recommended]` Alphabet `[0-9a-z]`, 12-char zero-padded seed with a
   1,000,000 step, mid-points by digit extension, invariant "a key never ends in the lowest digit",
   server re-keys a goal's list when a key would exceed 100 chars. Confirm the migration can seed it in
   pure SQL on the deployed D1 build; otherwise a one-shot script.
6. **Remove `WEEK_NOT_CURRENT` or keep it as an alias?** `[recommended]` Remove. Two codes for one
   refusal forks the client copy and the MCP recovery text.
7. **Do the `+` drawer and an Idea's "Task this week" gain a week picker?** `[recommended]` No. Both exist
   to get a thought out of the way in two seconds; a week choice is a decision and belongs on the
   planning screen. This is also the largest single reduction in blast radius available.
8. **Can focus sentences be re-ordered directly, or only by re-saving the plan?** `[recommended]` Only by
   re-saving — the field order *is* the order (R-plan-14). Per-field `Move up` / `Move down` buttons are
   free to add and need no new command; a second drag surface is not.
9. **Are a future week's tasks editable (title, done-condition, links) before the week arrives?**
   `[recommended]` Yes. Editing a plan is not completing work, and R-task-26 already keeps even done tasks
   editable. Only completion is blocked.
10. **Does an open task from this week appear when a future week is viewed?** `[recommended]` Yes —
    R-task-7 unchanged: an open task is visible in every week ≥ its origin. Next week honestly shows what
    you are already carrying into it. The carry chip is correct there (R-task-37), and no `carried` event
    is written for a week that has not happened (R-task-38).
11. **Is `planned N weeks ago` the right staleness signal, at a ≥2-week threshold?** `[recommended]` Yes:
    one muted line, on arrival only, no colour and no prompt. Anything more is the review wizard R-nav-14
    removed on purpose.
12. **Should the week picker's has-work dot exist (R-nav-18)?** `[recommended]` Yes. Without it a plan
    written for `+2` is invisible from every screen except `+2`, because future work is deliberately
    excluded from today's numbers.
